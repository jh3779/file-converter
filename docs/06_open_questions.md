## 가정 (Assumptions)
잠정으로 두고 진행한 전제. 틀리면 재검토 대상.
| ID | 가정 | 근거/리스크 |
|----|------|-------------|
| ASM-001 | 번들 LibreOffice 엔진으로 DOCX→PDF 정확도가 일반 사용자 기대치를 충족한다 | 복잡한 서식·한글 글꼴에서 차이 가능. 실제 문서 샘플로 검증 필요 |
| ASM-002 | 설치 용량 수백 MB는 "설치 간편함" 요구와 상충하지 않는다 (사용자가 택한 것은 '별도 프로그램 불요'이지 '소용량'이 아님) | 인터뷰에서 엔진 번들 선택으로 확인됨 |
| ASM-003 | 대상 파일 크기는 일반 사무 문서 수준(수십 MB 이하) — 초대형 파일 최적화는 MVP 범위 밖 | 대용량 CSV/PDF에서 성능 이슈 시 재검토 |
| ASM-004 | UI 언어는 한국어 우선 | 1차 사용자가 국내 일반인 |

## 결정 로그 (DEC-*)
확정된 결정과 근거. 임의 번복 금지.
| ID | 결정 | 근거 | 날짜 |
|----|------|------|------|
| DEC-001 | 기술 스택: **Python + PySide6(Qt) + PyInstaller 패키징 + LibreOffice 엔진 번들** | 변환 라이브러리 생태계가 가장 풍부한 단일 스택(openpyxl/pandas: CSV·XLSX·JSON, pdfminer/pdf2docx: PDF, pyhwp: HWP). 어차피 LibreOffice를 번들하므로(수백 MB) Python 런타임 용량은 무의미. Tauri/Electron은 변환용 Python 사이드카가 별도로 필요해 2중 스택이 됨. Qt는 mac 개발→Windows 배포 크로스 플랫폼 충족 | 2026-07-29 |
| DEC-002 | DOCX→PDF는 번들 LibreOffice headless 엔진 사용 (경량 자체 변환 대신) | 정확도 우선. "별도 프로그램 설치 불요" 조건은 번들로 충족 | 2026-07-29 |
| DEC-003 | HWP는 읽기 전용 (HWP→PDF/TXT/DOCX만, HWP 쓰기 미지원) | 오프라인 단독 구현의 현실적 범위 | 2026-07-29 |
| DEC-004 | 출력은 원본 폴더 + 이름 충돌 시 자동 리네임, 원본 절대 비수정 | 원본 보호 품질 기준. 저장 위치 선택 UI는 MVP 제외 | 2026-07-29 |
| DEC-005 | 일괄 변환 실패 시 계속 진행 + 결과 요약 | 대량 처리 흐름 유지 | 2026-07-29 |
| DEC-006 | 메인 UX는 원스크린 드롭존 (마법사·카테고리 방식 배제) | 3클릭 완결 단순함 | 2026-07-29 |
| DEC-007 | HWP 처리는 **hwplib**(Apache-2.0, main 브랜치 소스 빌드) + JRE 사이드카로 확정. pyhwp(AGPL)는 사용 금지.
